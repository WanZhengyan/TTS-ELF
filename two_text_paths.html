统一 TTS + S2T · 2026-10-11

两条文本通路

模型里有两份完全不同的文本表示，用的是两种完全不同的机制。把它们弄混，关于 cond 的问题就答不清楚。这一页先讲清这两条路，再给当前结构，最后是在「只用一个 transformer backbone」这个约束下真正值得做的改进。

你问的那个问题

token 怎么变成连续量

答案取决于问的是哪一条路。z_T 用的是一个冻结的预训练编码器，cond 用的是一张从零训练的查表——根本不是编码器。

z_T 通路 冻结编码器

T5 的 token id 过 t5-small 的 encoder，拿 last_hidden_state，再除以 0.2。

机制
6 层 transformer encoder，冻结（35.33M 参数，requires_grad_(False)）
词表
32,100 个 T5 sentencepiece token
形状
(B, 48) ids → (B, 48, 512) float
为什么除 0.2
ELF 的 latent_std。除的是编码器输出（std 0.1585 → 0.79），不是 embedding 表（std 17.26）。判据是让 ELF-B-owt 自己无条件采样，生成的 x₀ std 为 0.81–0.88 —— 只有 0.79 这一侧对得上。
分辨率
1 个 token ≈ 26.3 个 mel 帧

cond 通路 可训练查表

字符 id 直接查一张 nn.Embedding(40, 512)，然后过一个 RMSNorm(512)。没有编码器，没有上下文，没有注意力。

机制
一次查表，20,480 个可训练参数，初始化 std 0.02，第 0 行清零当 padding
词表
40 行，实际只用 38 个字符（index 2–39）：空格、a–z、' " . , ; : ! ? - ( )
形状
(B, 560) ids → (B, 560, 512) float
为什么要 RMSNorm
z_T 进来每维 std ≈ 1，而 std-0.02 的表要弱约 50 倍。实测早期 cond 只有 z_T 尺度的 1.14%，而且投影层并没有去补偿它，所以显式归一化到同一量级。
分辨率
1 个字符 ≈ 6.2 个 mel 帧（比 token 细 4 倍）

所以这张「text embedding」不是从任何地方来的 —— 它就是梯度训出来的，和模型其它权重一样。它唯一的输入是字符 id，唯一的作用是给 TTS 提供比 T5 token 更细的时间分辨率。

清浊对、同音异拼对自己聚到了一起。这不是设计出来的，是 TTS 的 mel 重建损失逼出来的 —— 对于预测频谱，b 和 p 确实几乎是同一件事。这也是为什么我一度认为去掉 cond 会伤 TTS。

当前结构

一个 backbone，两个任务，按位置分区

序列长 560 个位置，固定切成两段：位置 0–511 是 mel 区（512 帧 ÷ 93.75 Hz = 5.46 秒），位置 512–559 是 token 区（48 个槽）。token 区的起点固定在 512，不随音频长度浮动，这样它的 RoPE 位置不会漂。

每个位置上堆 5 个通道块，拼成一个 1736 维的向量喂进去。两个任务填的是同一个格子阵，但填的格子不同 —— 这是整个设计的核心，也是 Whisper 和 T5 能共用 z_T 这一行却不冲突的原因。

「第一行第二行」到底指什么

这是最容易问错的地方，因为两个任务的「第一行」不是同一件事：

  • TTS：条件是 z_T + cond（图中第 1 和第 5 行），目标是 z_V（第 3 行）。文本同时出现三次：字符级、帧级、token 级。
  • S2T：条件是 z_V（第 3 行，mel 区）加上 z_T 的 mel 区（第 1 行，但那里装的是 Whisper 不是 T5），目标是 z_T 的 token 区（第 1 行的右半）。

所以 z_T 这一行在 S2T 里既是条件又是目标 —— 左边 512 列是 Whisper 条件，右边 48 列是待生成的文本。这不是设计失误，是 hybrid 布局的全部要点：两个任务在同一个格子阵上换着填，backbone 一个字节都不用分叉。

结果

S2T 能用，TTS 还不行

先说一个今天刚发现的问题。10-10 17:04 我改了 collate（把转录随音频裁剪、并把 chars 按任务门控）。在那之前测的 TTS 音频和之后测的不可比。同一个 p_dp5 ckpt，旧代码给 gen WER 50.63，当前代码给 93.07。

所以我昨天说的「去掉 cond 让 TTS 从 50 掉到 89」是错的 —— 那个对比跨了代码版本。在同一套代码下，cond 保留和去掉的 TTS 都在 82–94 这一档。要得到干净结论，需要在当前代码下重训一个保留 cond 的模型，这正是 job 15971 在做的事。

audio CFG 白赚 3.67 个 WER 点，纯推理期，不用重训。但这里有个反直觉的结果：没有无条件分支的那个模型改善更大（−3.66 vs −2.80），绝对值也更好。那个作为伪证对照的模型本该不受引导影响 —— 它反而赢了。所以引导起作用的机制不是「兑现训练出来的无条件分支」，而是对比度放大，任何模型都支持。audio_drop_prob 因此是纯成本，应该设 0。

n=64 的 eval 偏乐观约 3 点。p_dp5 在训练期 n=64 上最后 5 次均值是 21.75%，在 n=288 上无引导是 25.09% —— 偏乐观 3.34 点。之前所有表里的 S2T 数字都要按这个偏移读。

改进方向

一个 backbone 不是限制，是已经做到的事

先确认这一点：现在两个任务共用 backbone 的程度是 100%。12 层里没有任何任务条件参数，一个双向 mask 服务两个任务，一次混合前向。唯一的任务专属参数是 4 个 task token，6,144 个参数，占 0.0058%。下面每一条改进都不碰这个结构。

  1. TTS 的 classifier-free guidance

    成本 零训练，纯推理 · 状态 job 15970 正在跑 · 依据 S2T 侧同一手法值 3.67 个 WER 点

    这是最该先做的，因为它免费。我今天才发现 --gamma 不是 CFG 而是 SDE churn（重加噪）—— TTS 方向在推理时从来没有任何引导。而 flow-matching TTS 用 CFG 是标准做法（Voicebox、E2-TTS 都是 w≈2）。无条件分支的机件本来就在（drop_text 把 T5 latent 和字符块一起清零），只是被当成一条独立 track 在跑，没去引导主路径。考虑到 UTMOS 已经接近天花板而 WER 还差 68 点，「内容不对」正是 CFG 最擅长修的那类问题。

  2. 把 decoder_prob 做成退火，而不是挑一个点

    成本 一个训练标志，零新参数 · 依据 实测这是个零和旋钮

    这个旋钮从 0.2 调到 0.5，S2T 好 5.2 个 WER 点，TTS 差 6.3 个。一个任务的收益几乎等于另一个的损失 —— 这就是单 backbone 真正的代价所在，而且它在目标函数的配比上，不在参数上。decoder_prob 是每行一次伯努利抽样，决定这一行算流匹配损失还是 CE 解码损失，两个任务共用同一次抽样。与其在这条线上挑一个妥协点，不如让它随训练退火：早期高一点把文本接地学牢，后期降下来把 mel 质量磨出来。这不改结构，只改训练课程。

  3. 给 Whisper 自己的列块

    成本 512 个输入列，约 26 万参数，backbone 不变 · 依据 这个选择从未被检验

    现在 Whisper 投影是加进 z_T 的（z_t = z_t + a），和 T5 共用同一组 512 列。位置上不冲突（实测重叠为 0），但这 512 列要承载两个尺度差很多的分布：T5 latent std ≈ 0.79，而投影输出实测是它的 2.5–2.7 倍，训练并没有把它拉平，反而从 2.03 倍涨上去了。我当初这么设计是为了骑在 ELF 预训练过的通道上，但「加进 z_T」和「单独开一块」这两种做法我从来没对比过 —— 之前测到的最大 S2T 改善是「有 Whisper vs 没 Whisper」，不是「放哪里」。

  4. 给 TTS 一个时长预测头

    成本 token 区上的一个线性头，backbone 共用 · 依据 现在的 TTS 不是真 TTS

    当前 TTS 是通过 t5_idx[j] = ⌊j·N/T⌋ 这个升采样率被告知目标时长的 —— T 来自真实音频的长度。所以它实际在做的是「文本 + 时长 → 语音」，不是「文本 → 语音」。真正的 TTS 需要自己预测时长。好消息是这完全可以留在一个 backbone 里：在 48 个 token 位置上挂一个头，预测每个 token 占多少帧，推理时用它算升采样率。

  5. 把序列拉长，并跑 LibriSpeech 全长

    成本 约 42 GB Whisper 预计算 + 6–8 小时训练 · 依据 现在没有任何数字可以对外比

    5.46 秒和 48 个 token 的上限意味着只能处理短句，而且从没在 LibriSpeech 全长上训过，所以 S2T 的 21.42% 没法和 ELF-S2T 的 10.50% 比，TTS 也没法和 Matcha-TTS 比。多说话人更是完全没解决：LibriSpeech 上 UTMOS 只有 1.765（给 30% prompt 也才 1.930），而 LJSpeech 是 3.23–3.69。缓存里已经有 spk 字段，但还没接进去。

我的判断是前两条值得立刻做完：第 1 条免费且目标明确（UTMOS 已够、WER 差太多，正是 CFG 的靶子），第 2 条直指单 backbone 的核心代价且不改结构。第 3、4 条是真正的架构改进但各需一轮训练。第 5 条是让结果可对外比较的前提，不改进任何东西。
